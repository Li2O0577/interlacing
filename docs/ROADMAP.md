# 路线图

已经商定、按顺序一项一项做的方向。每一项开始前先给出详细计划，批准后再动手。

## 已完成

- **0.14.0 拆开引擎、轻写法、文件夹节点。** 引擎内部按职责拆成几个部件；普通函数直接当节点，`@node`、协议可省、`run()` 一步运行；整个文件夹作为一个节点。

- **运行中按显式操作改图。** `ctx.change(Change())`：检查、立刻生效、写进日志、恢复时重做。

- **跨进程、跨机器的节点。** `serve_node` / `interlacing node-serve` 把节点放在它所在的地方常驻服务，图里用 `RemoteNode` 代表；TCP 上一行一个 JSON，带停止信号和用量；不在本机监听要令牌，图文件只能连允许的地址。流和调用仍然只在进程内。

- **协程节点。** `async def run` 的节点在引擎的事件循环上被 await，不各占一个线程，超时被取消；`await ctx.acall`。多线程时每个信封六七十微秒的开销来自 Python 线程交接，协程不会让同步节点变快，所以同步节点仍在线程里。模型接口目前还是同步的，以后需要时可以用标准库写异步 HTTP。

- **每个节点的开关。** 暂停、恢复、停止、重启，单个或成批；图里写明谁管谁，上级只能拨下面的节点；写进日志、恢复时保持。开关也管到进程外：别的进程里跑着的运行通过运行目录拨，`RemoteNode` 的远端停在它的下一步，外部程序跟着挂起（Linux、macOS），程序自己的时限也停表。这是“以 agent 为中心”计划的第 1 阶段。

- **常驻 agent 和任务栏。** 任何节点都能在激活中途收消息（`ctx.receive`，等的时候不占工作名额，互相等不会卡死）和存档进度（`ctx.commit`，中断后接着做）。在这之上，`AgentNode(resident=True)` 一直在，直到自己 `finish`：先发做好的部分、`wait` 等别人、任务栏（`plan`、`done`、`note`）。普通函数可以直接当 agent 的工具，自带 `time_left`。这是第 2 阶段。

- **更正。** `ctx.emit` 返回消息编号，`ctx.correct` 用新内容顶替：没读的直接换掉；读过的按收方的 `on_correction` 处理（程序重跑并把更正往下游传，agent 被告知后自己决定，或者不管）；图的输出原地改对。常驻 agent 有 `correct` 工具。这是第 3 阶段。

- **质疑。** 边上可以打开 `challenges=N`：下游只判断“符合预期与否”，不符合就 `ctx.reject` 驳回并等待，上游解释或者更正；agent 有默认提示和 `reject` / `explain` 工具，已经结束的上游会被叫回来答复；次数用完就用手上的值继续。一个端口接着几条边时可以点名驳回哪一条；驳回里带着同一次发出的其他消息的编号，上游可以一起更正。远端节点也能更正自己发的消息了。这是 3.5。

- **管辖和招人。** 常驻 agent 在允许时（`hire=N`，整次运行最多 N 个）按模板招下属，自动接好派活和回话的线，还能解雇、拨开关、查看团队、在团队内接线；下属的目录在上级目录下，名额不超过上级。底下是 `Change.ports` / `Change.manage`；节点内部那张图里的节点用路径名拨。下属失败时先交给上级（`oversees`），由上级决定重启、解雇还是放弃。这是第 4 阶段。

- **好上手。** 图的格式说明随包提供（`GUIDE`、`guide`、MCP `guide` 工具、`SpawnNode.tool()`），JSON 写法和 Python 一致（函数节点读签名、方法就地嵌套），写错时报错给出正确写法或可选项；`allow` 只放行允许模块里定义的函数。真实模型不看文档也能一次写对图。

## 早期引擎规划记录

以 agent 为中心的计划（[设计与分阶段计划](https://claude.ai/artifact/9NoHnubxG88ZNrSTFkqLbP)）第 1 到第 4 阶段都已做完。下一步做什么，等商量后再定；候选在下面。

### 该阶段的交付与验收

1. 用普通节点跑两种模拟审查：解释后继续、暂停受影响的接收者并修订。核对模拟调用数，并从答复中断处恢复一次。
2. 让 CI 检查两版手册的公开 API 表、示例一致性和执行结果。
3. 在已排空的基准运行中分步释放读取历史、发送历史与其余引擎引用，实测保留内存来源。
4. 归拢质疑的排队、领取和答复状态，保留现有调度行为。
5. 让 show 从完整日志行还原运行中的拓扑变更，输出按记录顺序的时间线及 Mermaid/DOT 图。旧日志没有的时间信息保持未知。

本地 2,048 条不同的 8 KiB 消息：队列峰值 2,048 条，tracemalloc 峰值约 18.2 MiB。排空后约 9.84 MiB；在一次性基准引擎上清除读取历史后约 0.58 MiB，再清除发送历史后约 0.13 MiB。数字依赖解释器和负载。保留历史支持更正；这组数据不足以决定为所有队列设置背压。

恢复试验：在 A 已记下暂停 B2、还未答复 B1 时终止进程。恢复后 B1 重新质疑一次，A 完成修订，B2 恢复，模拟用量仍为一次。这个试验支持沿用当前恢复语义；外部副作用仍需要幂等设计。

### 消息投递优化计划

1. 对照同一份工作负载，在 1 路与 8 路投递下分别测小消息和 64 KiB 正文。每次发送中，当多条边最终得到同一个内置 str 对象时，复用第一次投递算出的摘要。各条边照常编码、传输、编号和投递。用回归测试覆盖转换正文、自定义传输、可变值和连续发送。
2. 用突发生产者与慢消费者实测待处理数和内存峰值。区分排队与为了更正而保留的历史。根据真实模拟的观测，再决定是否给队列加可选背压。
3. 下次调整质疑逻辑时，将节点状态里属于质疑与答复的字段和转换收拢到一起，以暂停、答复和恢复的组合场景验证。

### 以后再看

这些不在上面的阶段里，等需要时再做：

- 下属的模板写成函数时，它的目录不会自动放进上级目录（写成描述时会）。
- 节点内部那张图里的节点，只有那张图在跑的时候才拨得到；拨的记录写在里面那次运行的日志里。
- 观测后续：跨嵌套子图的时间线；当前 `show` 查看一个运行目录的顶层日志。
- 流和调用跨进程（`Transport`）。现在节点可以在别处，但节点之间的边只在进程内。
- 模型接口改成异步 HTTP（标准库）。现在模型调用是同步的，在线程里跑。
- 暂停中的等待改成纯事件唤醒，不再轮询（现在线程每 0.1 秒、协程每 0.05 秒看一次）。
- 只用 `Engine`、不给日志时，剩下的全被暂停的运行会结束且没法接着跑；可以考虑这种情况下改成一直等开关拨回来。
- Windows 上暂停外部程序本身。现在只有节点在等，程序继续跑。
- 普通值输入的恢复后原位修订已用 A/B1/B2 验证；仍可扩展到自定义解码等输入。接上之前还没答复的驳回也能接着等（现在那次激活会重跑、重新判断）。
- MCP Inspector 图形客户端已完成模拟审查、查看依赖、答复和恢复。后续可在日常使用的桌面 AI 应用中验证模型自主选工具，并在真实模型服务上覆盖思考和图片输入。
